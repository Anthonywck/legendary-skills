# 反例集

每条都是**本 Skill 开发过程中真实出现过**的缺陷，不是假想场景。
改脚本时请对照检查，避免退回。

---

## ❌ 反例 1：把正文里的事件日期当成文档日期

**场景**：`【光刻机】杭州芯微影半导体…pdf`，页尾第 30 页附近写着

```
2017年5月26日，先进薄膜刻蚀和沉积设备全球领导者 Veeco Instruments 公司完成收购…
```

**错误实现**：「末两页全文搜索日期」→ 得到 `date: 2017-05`，
年份错了 6 年，且静默写进目录名。

**正确做法**（`_date_from_zone` + `C.date_line_of`）：

1. 只搜封面 6 行 + 落款 12 行，**不搜正文中段**
2. 该行必须「以日期为主体」：去掉数字与年月日后剩余文字 ≤ 6 字
3. 上述句子剩余「，先进薄膜刻蚀和沉积设备全球领…」远超阈值 → 拒绝

**自检**：拿任何一份 BP，问「这个日期所在的整行，除了日期还写了什么？」
如果还有一句完整的话，那就不是落款。

## ❌ 反例 2：把行业标杆公司的成立时间当成主体的

**场景**：BP 正文写

```
上海微电子装备（集团）股份有限公司成立于2002年3月，位于上海张江高科技园区
```

**错误实现**：`成立时间: [...成立于...]` 万能正则 → 抽出 `成立时间: 2002年`，
于是「杭州芯微影半导体」的 `key_facts` 里出现了别人的成立年份。

**正确做法**：要求主语是「公司 / 本公司 / 我们」

```python
r"(?:^|[。；;\n])\s*(?:公司|本公司|我们)(?:成立|创立)于\s*((?:19|20)\d{2}年?...)"
```

**为什么不能靠「最近的公司名」判断**：BP 里主语省略极常见，做不出可靠推断。
宁可 `null`，不可错填——错误的 `成立时间` 会被下游当作事实引用。

## ❌ 反例 3：别名抽取取错主体

**场景 A**：某 BP 正文先提到「中国航天科技集团有限公司」，
错误实现「取正文第一个全称」→ `alias_full` 变成航天科技集团。

**场景 B**：PDF 折行导致文本是
`……传播科技股份有限公司是一家……`，
正则从中间匹配出「梭科技股份有限公司」。

**正确做法**（双保险）：

1. `alias_full` **必须包含主体名**（`subject_key` 子串匹配）才采纳
2. 正则左边界必须是「非公司名字符」，左首不能是 `的是为由在和及称`

**退而求其次**：`alias_full: null` 完全可接受。错的全称比没有更糟——
用户 grep 一个错误全称会得到「命中」，从而相信了错误信息。

## ❌ 反例 4：用总字数判断扫描件

**场景**：`中熵科技 Pre-A+` 26 页扫描件，前 25 页 0 字符，第 26 页有一段推广水印文案。

**错误实现**：`if len(text) == 0: needs_ocr` → 总字数 383 > 0 → 判为 `ok`，
于是 96% 的内容永远不会被检索到，而索引显示一切正常。

**正确做法**：按**页覆盖率**判

```python
coverage = pages_with_text / total_pages
if coverage < 0.30: status = "needs_ocr"
```

**通用原则**：判断「有没有内容」时，优先看**分布**而不是**总量**。

## ❌ 反例 5：放行乱码正文去抽取

**场景**：`中博芯半导体科技.pdf` 字体缺 ToUnicode，抽出的是
`ԗцЗԧ৾ / ԠجѼय۪`。

**错误实现**：只要有文本就往下抽 → 乱码里仍能匹配到「估值」「亿元」等字样，
产出通篇臆造的关键事实。

**正确做法**：

1. 检测异域脚本字符占比（西里尔/亚美尼亚/格鲁吉亚等），≥ 15% 判 `encoding_error`
2. `usable_text()` 只对 `status == "ok"` 返回正文，其余一律返回空串
3. 失败态下 `summary` 写固定警示语，`key_facts` 只剩「页数」

**衡量指标用错也会出事**：不要用「中文占比低」判断乱码——
英文原版报告的中文占比本来就低，会被误杀。

## ❌ 反例 6：主体推断把整句产品名吃进去

**场景**：`【芯片抛光】深圳烯钻科技 半导体芯片化学机械平坦化CMP抛光耗材项目商业计划书.pdf`

**错误实现**：只按「空格+连字符」分隔 → 主体变成
`深圳烯钻科技半导体芯片化学机械平坦化CMP抛光耗材`（26 字），
与另一份「深圳烯钻科技 -…」的主角对不上，同主体文档无法归并。

**正确做法**：任意空白或标点都是分界；主体长度上限 20 字。

**代价**：可能把极少数「英文名 + 中文名」连写的公司名截断。
这不是问题——截断后仍可通过 `overrides.yaml` 纠正，而吃掉产品名会让归并集体失效。

## ❌ 反例 7：用二进制哈希识别重复

**场景**：`【芯片抛光】深圳烯钻科技…` 与 `【芯片材料】深圳烯钻科技…`，
文件大小差 322 字节，二进制 sha1 不同，但**正文完全相同**（同一份材料的两次导出）。

**错误实现**：`source_sha1` 相同才判重复 → 漏判。

**正确做法**：两个哈希分工

| 哈希 | 用途 |
| --- | --- |
| `source_sha1`（二进制） | 判**改名**：同一份字节换了名字 |
| `text_sha1`（归一化正文） | 判**重复**：不同字节、同样内容 |

两者混用会同时导致「改名漏判」和「重复漏判」。

> 这个词条同时是「词表选择」问题：`text_sha1` 若在正文前混入各不相同的
> 元数据头，重复判定也会全部失效。必须对**源文件正文**取哈希。

## ❌ 反例 8：`--rebuild` 把孤儿产物当陈旧文件删掉

**场景**：源文件被删除 → 产物标 `missing/orphaned` → 下次 `--rebuild`。

**错误实现**：重建时「索引里没有的产物一律删除」→ 孤儿产物被物理删除，
索引里 `missing` 痕迹也消失。**这直接违反「源删除时不得静默丢弃产物」。**

**正确做法**：

1. `--rebuild` 重建后，扫描产物自身的 `source_path`
2. 源不存在的，重新登记为 `missing/orphaned`
3. 陈旧清理只删「`by_topic` 下 + 首行 `---` + 前 3000 字含 `source_path: datas/`」的文件

**为什么用「读产物」而不是「读历史索引」**：重建的口径必须是「从目录推导」，
而不是「沿用缓存」。产物文件本身就是目录的一部分，读它不算依赖历史索引。

## ❌ 反例 9：改名时新建索引行

**错误表现**：改名后索引从 3 行变成 4 行——旧路径标 `missing`，新路径标 `renamed`。

**原因**：失联判定用的是「扫描到的路径集合」，改名时新路径进入了集合，
旧路径没有。

**正确做法**：改名场景把 `renamed_from` 也加入「已见路径」集合，
旧路径不再生成 `missing` 行。改名是**原地更新**。

**另一个连带问题**：改名时新算出的 `md_path` 会撞上旧行占着的同一个路径，
路径分配器会误以为「被别的文件占用」而追加哈希后缀。
必须在判定改名后先释放旧行的路径占用。

## ❌ 反例 10：进程持有源文件句柄

**场景**：Windows 上解析 PPTX 后，用户无法改名/移动/删除该文件。

**错误实现**：`Presentation(str(path))` —— python-pptx 保留底层 zip 句柄。

**正确做法**：读进内存再解析

```python
prs = Presentation(io.BytesIO(path.read_bytes()))
```

DOCX 同理。这既是「原件只读」的一部分，也是让后续同步能正常移动文件的前提。

## ❌ 反例 11：日期正则匹配不到 CJK 部首字形

**场景**：PDF 里的 `2022年5⽉` 用的是 U+2F49（KANGXI RADICAL MOON）而非 `月`。
`[年月日]` 直接匹配不到。

**正确做法**：先 `unicodedata.normalize("NFKC", text)`，
部首字形会折回标准汉字。

**副作用**：NFKC 还会折全角字母/数字，对本场景有益无害。

## ❌ 反例 12：把 `pymupdf4llm` 当默认解析器

**场景**：19 页 BP 抽取从 5 秒变成数分钟。

**原因**：PyMuPDF 2.0 起 `pymupdf4llm.to_markdown` **默认启用 RapidOCR**，
逐页跑 OCR；且其参数列表用 `**kwargs` 透传，没有稳定的关闭开关。

**正确做法**：默认走「PyMuPDF 纯文本按页拼装」，确定性高、快；
需要更强结构时用环境变量显式开启 `FDS_LLM_MARKDOWN=1`。

## ❌ 反例 13：为了「填满」而编造字段

| 错误做法 | 后果 |
| --- | --- |
| 只有年月，补成 `2022-05-01` | 日期看起来精确，实际是假的；时间回溯排序被污染 |
| 行业报告填 `round: null` 改成 `"不适用"` | 字段类型不一致，grep 与解析都要加特例 |
| 抽取不到估值，就写行业平均值 | 直接把错误数据写进知识库 |
| `subject` 抽不到，用「未知公司」 | 与 `unknown` 语义冲突，且无法归并 |

**正确做法**：`null` / `unknown` 是合法且被推荐的取值。
`validate_output.py` 不会因为字段为空而报错——它只检查**已填的值是否自洽**。

**用户补充规则（非踩坑记录）**：提取时不得编造数据，也不得「随意填充」——
包括用模板默认值、行业均值、同主体其它文档的值来填空。抽不到的字段就是空。

## ❌ 反例 13b：发现原件有错，就「顺手」改掉

> **说明**：本条来自用户明确提出的约束，不是实测踩坑记录。
> Skill 原版的「防臆造」只覆盖「抽不到别补」，没有覆盖「抽到了但原文可能写错」这一半。

| 错误做法 | 后果 |
| --- | --- |
| 发现投前/投后估值口径疑似写反，产物里直接按自己的理解改过来 | 知识库与原件对不上，用户 grep 到的值在原文件里搜不到，无法回溯 |
| 发现日期晚于落款，就把 `date` 改成一个「看起来合理」的时间 | 同反例 1，且这次是主动造假 |
| 发现文件名像笔误，直接改名或移动 | 打乱 `files_index.csv`，下游按原路径引用全部失效 |
| 凭一次推理就报告「原文有误」 | 误报，用户开始怀疑整套索引 |

**正确做法**（细则见 `references/extraction-sop.md` ⑨）：

1. 产物按原文如实抽取，**一个字段都不改**
2. 至少两条独立依据交叉验证（文档内其它章节 / 同主体其它文档 / 算术与公开事实）
3. 验证通过后，以「疑点 + 原文 + 依据 + 建议」的形式报告给用户
4. **只给建议，不执行修改**——改不改、怎么改，由用户自己决定

**通用原则**：结构化工具的职责是「让人找到原文」，不是「替原文做校正」。
两者混在一起，知识库就失去了可信的参照物。

## ❌ 反例 13c：因为疑点而卡住产出

**错误做法**：发现某份 BP 有疑似错误，就先不生成 `.md`，等用户确认后再继续。

**正确做法**：**照常产出**，疑点单独报告。知识库缺一份文件的代价，比多一条保留原文的
错误数据更大——后者用户可以自己判断，前者用户根本不知道有这份文件。

这与「单点失败不中断」是同一个原则：**结构和提示分开处理，互不阻断**。

## ❌ 反例 14：用总字数判断扫描件是否需要 OCR（再次踩坑）

在加入 OCR 能力后又遇到一次：某 27 页券商报告，前 26 页无文本层，
第 27 页的免责声明有 200 字。按总字数判断会判为 `ok`，
实际 96% 内容不可检索。

**正确做法**：始终用「有文本层的页占比」判，阈值 0.30。

## ❌ 反例 15：OCR 内联导致全量变慢十倍

**现象**：168 份文件里 8 份扫描件，启用内联 OCR 后全量从 2 分钟变成 25 分钟。

**原因**：单页约 4 秒，扫描件动辄 20–125 页。少数文件拖垮整批。

**正确做法**：两阶段。阶段一快速落地（扫描件只标 `needs_ocr`），
阶段二用 `run_ocr.py` 单独补，可分批、可断点续跑。

**通用原则**：批量任务里，「慢且只影响少数样本」的操作应该独立成单独一轮，
不要内联进主循环。

## ❌ 反例 16：OCR 日志污染 CLI 的 JSON 输出

**现象**：`extract.py --json` 输出被 `[INFO] [RapidOCR] Using engine_name…` 污染，
下游 `json.load` 直接报错。

**原因**：RapidOCR 默认把 INFO 日志打到 stdout，且部分版本直接 `print`。

**正确做法**：初始化与推理都套 `contextlib.redirect_stdout(sys.stderr)`，
并把它的 logger 降到 WARNING。

**通用原则**：CLI 工具的 stdout 是**数据通道**，任何库的诊断输出都必须赶到 stderr。

---

## ❌ 反例 17：`--limit` 试跑把未扫描文件误标为「源已失联」

**现象**：`sync.py --rebuild --limit 5` 的报告里出现「源已失联 4 份」。

**原因**：失联判定只看「索引有、本轮没扫到」。`--limit` 让本轮只看到 5 份，
其余全被判成 missing，而且会写进产物的 `source_available: false`。

**正确做法**：只有「真正全量」（无 limit / pick）才判失联；
部分试跑时，未扫描到的旧行原样保留、状态不动。

**通用原则**：任何「缺失判定」都必须先确认「本轮的观察范围是全量的」。

## ❌ 反例 18：死代码删除连带删掉了被依赖的函数

**现象**：拆分 `build_frontmatter.py` 时清理重复定义，把 `usable_text` 一起删了，
它在 `facts.py` 里还被用着，导致所有文件报 `NameError`。

**教训**：

1. 删除任何定义前先 `grep` 全目录，确认没有被 import
2. 把「被多处使用的判定函数」放在最底层模块（这里是 `extract.py`），
   而不是放在某个业务模块里顺带定义

## ❌ 反例 19：`key_facts: []` 被校验器误解析

**现象**：`key_facts: []` 被简单的前端解析器当成字符串 `"[]"`，
遍历时得到 `"["` 和 `"]"`，报「条目不合法」。

**正确做法**：解析器显式处理 `[]`（空列表）与 `[a, b]`（行内列表）两种写法，
不能只认「缩进多行列表」。

**通用原则**：自己写 YAML 子集解析器时，必须覆盖序列化的**所有**输出形态。
更稳妥的做法是序列化端固定只输出一种形态（本 Skill 已如此：空列表写 `[]`，
非空写缩进多行）——解析端仍需兼容，以防历史产物。

## ❌ 反例 20：运行报告用 `.md` 存放

**现象**：`_index/last_run_report.md` 被 `glob("**/*.md")` 当成知识产物命中。

**正确做法**：报告用 `.txt`。`_index/` 下不允许出现 `.md`，
`validate_output.py` 的 `I5_INDEX_NOT_MD` 会检查这一点。

**通用原则**：只要检索靠 glob，就要给「非知识文件的产出物」选一个不会撞扩展名的格式。

## ❌ 反例 21：`--rebuild` 把阶段二 OCR 的成果打回去

**现象**：做完 20 分钟 OCR，`needs_ocr` 归零；再跑一次 `--rebuild`，
8 份扫描件全部退回 `needs_ocr`，OCR 成果被抹掉。

**原因**：`--rebuild` 的实现是「全部重抽」，而阶段一默认不开 OCR
（这是刻意的，为了速度）。重抽 = 重新走阶段一 = 又变回未 OCR 状态。

**正确做法**：「重建索引」不等于「重解析每一份正文」。源文件未变更时：

- 产物 `md_status == ok` → 直接沿用，不重抽
- 降级 / 失败态 → 重试一次（也许依赖修好了）

```python
def _needs_reextract(prior, mode):
    status = prior.get("md_status", "").lower()
    if status == "ok" or status.startswith("orphaned"):
        return False
    return True
```

**通用原则**：任何「全量重建」都要想清楚——重算的单位是**索引**还是**产物**。
把昂贵且可能不可逆的处理（OCR）混进无脑重算里，一次误操作就白跑。

## ❌ 反例 22：OCR 后不清空旧的 `duplicate_of`

**现象**：补 OCR 后正文完全变了（从空白变成 1 万字），
但 `duplicate_of` 还是按旧正文算出来的结论。

**正确做法**：OCR 改动了正文 → 正文哈希与相似度都失效 →
必须重跑去重后置阶段，而不是原样保留旧结论。

**通用原则**：任何改变产物内容的操作，都要把「基于内容派生的字段」一并重算。

## ❌ 反例 23：改了规则却不重新抽取

**现象**：给 `taxonomy.yaml` 加了 `SHEET` 类型，重跑 `--rebuild`，
产物还是旧的 `OTHER` —— 「跳过未变更 N 份」，改动等于没改。

**原因**：跳过判定只看源文件是否变化（size + sha1），不看**判定规则**是否变化。

**正确做法**：记录 `taxonomy.yaml` 的内容哈希到 `_index/.rules_fingerprint`，
本轮哈希与上次不同就强制重抽全部文件。

**通用原则**：任何「输入」都包含两部分——数据与规则。
只比对数据会让配置变更静默失效。

---

## ❌ 反例 24：用正文 50 字阈值判断表格是否有效

**现象**：3 行 3 列的对照表 TSV 只有 48 字，被判成 `empty`。

**原因**：表格的「字数」远低于同等信息量的散文。一行 `赛道 | 代表企业 | 备注`
的信息密度很高，但只有十几个字。

**正确做法**：表格类用「有没有数据行 / 数据单元格」判定，不套用正文字数阈值。

**通用原则**：阈值必须匹配数据的形态。同一把尺子量散文和表格必然出错。

## ❌ 反例 25：`except Exception` 吞掉 NameError，把代码缺陷伪装成数据问题

**现象**：`maintenance.py` 漏了 `import shutil`，`_move_md` 抛 `NameError`。
被 `except Exception` 捕获后只写进 `errors.log`，表现为「3 份文件处理失败」，
索引里还留下 `missing/orphaned` 的坏行。

**正确做法**：`NameError` 只可能来自代码缺陷（漏 import、拼错变量），
不可能由畸形数据触发。遇到就直接 `SystemExit` 中止整批，把根因顶到用户面前。

```python
if isinstance(exc, NameError):
    raise SystemExit(f"检测到代码缺陷（{exc}），已中止批次") from exc
```

`AttributeError` / `TypeError` 则仍按单点失败处理——畸形数据也可能触发它们。

**通用原则**：「单点失败不中断」只适用于**数据**问题。
代码缺陷必须立刻中断，否则每个文件都会失败一遍，把真正的原因埋进日志里。

## ❌ 反例 26：路径变化时先写新文件再移动旧文件

**现象**：规则变更导致落位从 `A/x.md` 变到 `B/x.md`，
结果两处都有文件，索引只认一处，另一处成了孤儿。

**原因**：`write_md(新路径)` 之后再 `_move_md(旧路径 → 新路径)`，
移动会把刚写好的新文件覆盖或触发冲突。

**正确做法**：**先移动，再写入**。移动负责清掉旧路径，写入负责产生新内容。

## ❌ 反例 27：用系统 Python 跑 sync，把所有产物判成 unsupported

**现象**：全量重建报告里 169 份文件变成 `degraded:unsupported`，
`extract.py` 单个跑显示 `ModuleNotFoundError: No module named 'pymupdf'`。

**原因**：本 Skill 的依赖装在项目内 `.venv-doc/`，而 PATH 上的 `python`
是 pyenv 的系统解释器。`formats.yaml` 里 `pymupdf` 缺失 → 解析器不可用 →
**判定为 unsupported**。

**为什么特别危险**：`unsupported` 不是失败退出，重建照常「成功」，
然后用空正文把**已有的好产物逐份覆盖**。数据没有丢（源文件还在），
但 20 分钟的 OCR 成果和全部元数据被一次性抹掉。

**正确做法**：

1. 执行前先跑 `check_env.py`，用「可用解释器」那一行给出的路径
2. 不要依赖 PATH 上的 `python`；用 `.venv-doc/Scripts/python.exe`
3. 破坏性重建前先 `cp -r datas-md datas-md.bak-$(date +%Y%m%d)`

```bash
.venv-doc/Scripts/python.exe .claude/skills/funding-doc-structurer/scripts/check_env.py
```

**通用原则**：当「依赖缺失」被设计成一种**降级状态**而不是**中止**时，
它就会从「跑不起来」变成「跑起来但把好数据写坏」。这类降级必须有闸门——
`required` 依赖缺失时应当退出，而不是继续写盘。

## ❌ 反例 28：`--rebuild` 跳过 ok 产物，改了模板等于没改

**现象**：把「原文证据」表从两列改成三列、给产物加了空白清洗，
`sync.py --rebuild` 报告「新处理 5，跳过未变更 167」——三列证据表只出现在 5 份里。

**原因**：同反例 23（改了规则却不重新抽取）。`--rebuild` 的跳过判定只看源文件，
产物模板变了它不知道。这次连 `taxonomy.yaml` 都没动，规则指纹也拦不住。

**正确做法**：用 `--force-render` 显式重渲染全部产物。

```bash
.venv-doc/Scripts/python.exe .../sync.py --rebuild --force-render
```

它与「删掉 datas-md 重来」的区别：**不会把 OCR 成果打回 needs_ocr**，
因为它只跳过「源未变更 → 复用旧产物」这一步，不改变解析与 OCR 的判定。

**配套**：清洗规则与证据格式应纳入 `validate_output.py`（`T1`–`T7`），
让「模板变更没生效」在校验阶段就暴露，而不是等人去 grep。
