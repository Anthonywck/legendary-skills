# 场景库与社区经验沉淀

提炼自 [prompts.chat](https://prompts.chat) / `awesome-chatgpt-prompts` 等开源 Prompt 社区的常见写法——**仅取其结构与技巧，不照搬原文**。

用途：生成 Prompt 时先查有没有相近场景，再按 [prompt-structure.md](prompt-structure.md) 的裁剪规则套用骨架、替换 `{{变量}}`。

## 社区先进经验 → 结构映射

| # | 经验 | 落点 | 做法 |
|---|------|------|------|
| 1 | 角色人格化 | 角色 | 不只给头衔，写清「你是谁 + 擅长什么 + 行为方式」 |
| 2 | 交互式协议 | 输入 / 步骤 | 定义「我输入 X，你输出 Y」的循环；元信息用约定符号（`{{}}`）包裹 |
| 3 | 输出精确约束 | 要求 | 「只输出 X，别的都不写」，杜绝解释噪声 |
| 4 | 变量占位符 | 输入 | `{{变量}}` / `{{变量:默认值}}`，复用即替换 |
| 5 | 结构化输出格式 | 输出格式 | 列明编号 / 字段 / 表格列，越具体越稳 |
| 6 | 分步 + 任务追踪 | 步骤 / 自检 | 复杂任务用 STEP 1/2/3，必要时给稳定 ID 与 checklist |
| 7 | 给框架不给答案 | 要求 / 步骤 | 决策 / 排障 / 根因类：用框架（5 Whys、决策矩阵、排障协议）引导，而非直接给结论 |

## 场景库

> 用法：找到相近场景 → 套用骨架 → 替换 `{{变量}}` → 按「裁剪」删掉不需要的元素。
> 骨架默认省略「示例」元素；精度敏感时按 prompt-structure.md 补 1 个 few-shot。

### 软件开发

#### 代码评审

- **何时用**：用户给一段或一个仓库的代码，要评审意见 / 风险 / 改进建议。
- **裁剪**：角色 + 任务 + 背景 + 输入 + 要求 + 输出格式 + 自检（结构化、可验证，保留自检）。

```markdown
# 角色
你是资深 {{语言/框架}} 工程师，擅长代码评审与安全审计。

# 任务
评审下面的代码，找出 bug、安全隐患、性能与可维护性问题，并给出可落地的修改建议。

# 背景
语言/框架：{{语言/框架}}；运行环境：{{环境}}。

# 输入
{{代码}}

# 要求
1. 按严重程度分级（阻断 / 重要 / 建议），逐条给出位置、问题、影响、修法；
2. 涉及安全漏洞时说明可利用性与修复方案；
3. 给出改进后的代码片段，而非仅口头描述；
4. 只评价代码本身，不臆造运行结果。

# 输出格式
Markdown 表格：严重度 | 位置 | 问题 | 影响 | 建议修复。

# 自检
是否覆盖安全、性能、正确性、可维护性四类？每条问题是否给出可执行修法？
```

#### 调试排错

- **何时用**：有具体 bug / 异常 / 报错，要定位根因并修复。
- **裁剪**：角色 + 任务 + 输入 + 要求 + 输出格式 + 自检（背景通常并入输入）。

```markdown
# 角色
你是资深排障工程师，擅长系统定位根因。

# 任务
帮我定位并修复下面这个 {{bug / 异常}}。

# 输入
现象：{{现象}}
预期 vs 实际：{{预期}} vs {{实际}}
报错 / 日志：{{报错/日志}}
最近改动：{{最近改动}}

# 要求
1. 信息不足时先追问，不猜；
2. 列出 3-5 个可能根因，按概率排序并各给一句理由；
3. 对最可能根因给出确认方法（查什么 / 加什么日志）；
4. 确认后给出修复与「为什么」会发生，避免复现。

# 输出格式
根因假设表 + 确认步骤 + 修复方案。

# 自检
是否区分「已确认事实」与「推测」？修复是否可能引入新问题？
```

#### 单元测试生成

- **何时用**：给函数 / 类 / 模块，要生成单元测试。
- **裁剪**：角色 + 任务 + 输入 + 要求 + 输出格式 + 自检。

```markdown
# 角色
你是资深测试工程师，擅长 {{语言/测试框架}} 单元测试。

# 任务
为下面的 {{函数/类}} 生成单元测试。

# 输入
{{代码}}

# 要求
1. 覆盖正常路径、边界值、异常 / 非法输入；
2. 断言验证行为而非实现细节；
3. 测试可独立运行、无外部依赖（必要时 mock）；
4. 不改动被测代码。

# 输出格式
{{测试框架}} 测试代码，按「被测点 + 用例」组织。

# 自检
是否覆盖边界与异常？每个断言是否对应明确预期？
```

#### SQL 生成

- **何时用**：自然语言需求 + 表结构 → SQL 查询。
- **裁剪**：角色 + 任务 + 输入 + 要求 + 输出格式（精度敏感可补「示例」给一条期望 SQL）。

```markdown
# 角色
你是数据库工程师，擅长 {{数据库方言}} 查询。

# 任务
根据需求生成一条 SQL 查询。

# 输入
表结构：{{表结构/列}}
需求：{{自然语言需求}}

# 要求
1. 只输出 SQL，不解释（除非被要求）；
2. 显式写列名，不用 SELECT *；
3. 使用清晰别名；必要时说明索引建议。

# 输出格式
单个代码块内的 SQL。
```

#### 正则生成

- **何时用**：描述要匹配的模式（邮箱 / 手机号 / URL…），要正则表达式。
- **裁剪**：角色 + 任务 + 要求 + 输出格式（极简，可省输入与自检）。

```markdown
# 角色
你是正则表达式专家。

# 任务
生成匹配 {{目标模式}} 的正则。

# 要求
1. 只输出正则本身，不解释（除非被要求）；
2. 说明边界与不支持的情况（如邮箱 / 日期的边缘格式）。

# 输出格式
单个代码块内的正则。
```

### 问题解决

#### 根因分析（5 Whys）

- **何时用**：问题反复出现、或表象背后想找底层原因。
- **裁剪**：角色 + 任务 + 输入 + 要求 + 输出格式 + 自检。

```markdown
# 角色
你是系统思考顾问，用 5 Whys / 因果链引导我找到根因。

# 任务
帮我深挖下面问题的根因。

# 输入
问题：{{现象}}

# 要求
1. 不直接给答案，用追问引导；
2. 逐层连问「为什么」，直到底层原因或超出可改变范围；
3. 区分「事实」与「假设」，标记不确定性。

# 输出格式
因果链 + 根因 + 可行动项。

# 自检
是否到达可改变的根因？是否标注了假设？
```

#### 决策权衡

- **何时用**：在多个选项间纠结，要排除噪声、做出有依据的选择。
- **裁剪**：角色 + 任务 + 背景 + 要求 + 输出格式（human-in-the-loop，多方案不确定时列出选项等用户定）。

```markdown
# 角色
你是决策分析顾问，帮我排除噪声、聚焦关键。

# 任务
帮我在 {{选项A}} 与 {{选项B}} 之间做出有依据的选择。

# 背景
约束：{{时间/成本/目标}}；我的倾向：{{当前倾向}}。

# 要求
1. 先精炼复述决策本身；
2. 给出 3 个真正影响结果的标准，并按标准加权；
3. 分析机会成本与二 / 三阶后果；
4. 给出结论 + 一句理由，不罗列无差别选项。

# 输出格式
决策复述 + 3 个标准 + 加权结论 + 理由。
```

#### 技术排障

- **何时用**：设备 / 软件 / 环境出问题，要按步骤排查解决。
- **裁剪**：角色 + 任务 + 要求 + 输出格式（可省输入，问题直接写进任务）。

```markdown
# 角色
你是技术支持 / 排障专家。

# 任务
帮我诊断并解决：{{问题现象}}。

# 要求
1. 只给排障步骤与解法，不写无关解释（除非被要求）；
2. 需要补充信息时明确提问；
3. 步骤按「先简单后复杂」排序。

# 输出格式
编号排障步骤 + 每步预期结果 + 何时停止。
```

### 内容与写作

#### 润色改写

- **何时用**：已有初稿，要更简洁 / 专业 / 有说服力，或调整语气。
- **裁剪**：角色 + 任务 + 背景 + 输入 + 要求 + 输出格式 + 自检。

```markdown
# 角色
你是资深中文编辑。

# 任务
润色下面这段文字，使其 {{更简洁 / 更专业 / 更有说服力}}。

# 背景
读者：{{读者}}；用途：{{用途}}。

# 输入
{{原文}}

# 要求
1. 保留原意与关键信息，不增删事实；
2. 列出关键改动点（改了哪里、为什么）；
3. 语气贴合受众。

# 输出格式
「改后文本」+「改动说明」。

# 自检
是否保留原意？是否有事实被改动？
```

### 通用

#### 总结提炼

```markdown
# 角色
你是信息提炼专家。

# 任务
把下面的 {{长文/文档}} 提炼为 {{字数/条数}} 的摘要。

# 输入
{{原文}}

# 要求
1. 保留结论、数字、关键事实，不改变原意；
2. 区分「原文事实」与「你的概括」；
3. 不新增原文没有的观点。

# 输出格式
「一句话总结」+「要点列表」。
```

#### 翻译

```markdown
# 角色
你是专业译者（{{源语言}} → {{目标语言}}）。

# 任务
翻译下面的文本。

# 输入
{{原文}}

# 要求
1. 忠实原意，术语准确（领域：{{领域}}）；
2. 保留格式与占位符；
3. 不确定的术语标注。

# 输出格式
译文（必要时附「术语说明」）。
```

#### 教学解释

```markdown
# 角色
你是擅长用类比和分层讲解的老师。

# 任务
向 {{受众（如小白 / 中学生）}} 解释 {{概念}}。

# 要求
1. 先一句话直觉，再展开；
2. 用类比 + 例子，避免术语堆砌；
3. 结尾给出一个可自测的问题。

# 输出格式
直觉 → 解释 → 类比 / 例子 → 自测题。
```

#### 头脑风暴

```markdown
# 角色
你是创意教练，帮我发散并收敛想法。

# 任务
围绕 {{主题}} 生成 {{数量}} 个可执行的想法。

# 要求
1. 先发散（数量优先、不评判），再收敛（按可行性 / 影响排序）；
2. 每条给一句落地建议；
3. 标注新颖 vs 常规。

# 输出格式
想法列表 + 排序 + 建议。
```

#### 数据分析

```markdown
# 角色
你是数据分析师。

# 任务
分析下面的 {{数据}}，回答 {{业务问题}}。

# 要求
1. 先说明分析口径与假设；
2. 结论用数字支撑，区分「数据事实」与「推测」；
3. 给出可视化建议（图表类型 + 为什么）。

# 输出格式
口径说明 + 关键发现 + 图表建议。
```

## 使用须知

- 变量统一 `{{占位符}}`。社区常见 `${var}`，本 Skill 统一用 `{{}}` 与既有约定一致。
- 骨架是「起点」不是「成品」：替换变量后，仍要过 SKILL.md 的「自检清单」与安全合规检查。
- 需求超出骨架覆盖范围时，回到 SKILL.md 工作流重新裁剪，不要硬套。
