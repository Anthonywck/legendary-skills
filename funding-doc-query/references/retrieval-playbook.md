# 检索 Playbook

## 一、路径定位

**唯一入口**：`datas-md/by_topic/`，**恒限定 `*.md`**。

```
by_topic/{赛道}/{年份}/{DOC_TYPE}/{日期}_{DOC_TYPE}_{主体}_{版本}[_{状态}].md
```

赛道闭集：半导体 / 新材料 / 新能源 / 企业服务 / 节能环保 / 其他
类型闭集：BP / REPORT / WHITEPAPER / DOC / NOTE / OTHER

### glob 组合（按收窄程度从高到低）

| 已知条件 | glob |
| --- | --- |
| 赛道 + 类型 | `datas-md/by_topic/{赛道}/**/{DOC_TYPE}/*.md` |
| 赛道 + 年份 | `datas-md/by_topic/{赛道}/{年份}/**/*.md` |
| 仅赛道 | `datas-md/by_topic/{赛道}/**/*.md` |
| 仅类型 | `datas-md/by_topic/**/{DOC_TYPE}/*.md` |
| 仅年份 | `datas-md/by_topic/**/{年份}/**/*.md` |
| 全库（最后手段） | `datas-md/by_topic/**/*.md` |

**禁止**：

- `datas-md/**/*.md`（会把 `_index/` 与潜在的同级目录卷进来；实测 `_index/` 无 `.md`，
  但依赖这个巧合是脆弱的）
- 任何覆盖 `datas-generator/` 的 glob（那是生成物，不是知识源）
- 用 `_index/*.csv` 做内容检索（它是派生缓存，可能与产物不同步）

### 全库规模与预算（实测基线）

| 项 | 值 |
| --- | --- |
| 产物总数 | 172 份 `.md` |
| 单轮 read 上限 | 8 份 |
| 赛道分布 | 半导体 159 · 新材料 5 · 其他 4 · 新能源 2 · 企业服务 1 · 节能环保 1 |
| 类型分布 | BP 84 · REPORT 73 · WHITEPAPER 11 · DOC 2 · NOTE 1 · OTHER 1 |

赛道分布**极度倾斜**：任何跨赛道聚合题，半导体都会压倒其余。聚合题必须先声明
「本库以半导体为主」，否则「某技术有哪些公司」的答案会被误读为全市场结论。

read 份数不足时，**先报告未读清单**，不要假装读过；覆盖报告的「未纳入」栏必须填。

## 二、三级检索

### P1 · 元数据层

范围：YAML frontmatter + `## 元数据速查` + `## 关键事实` + `## 摘要`。

```
grep("投后估值", "datas-md/by_topic/半导体/**/BP/*.md")
```

用途：**定位与过滤**，不是答案。P1 命中只说明「这份文档可能相关」。

### P2 · 正文层

范围：`## 正文` 之后（按 `### 第 N 页` 分节）。

```
grep("龚胜", "datas-md/by_topic/半导体/2021/BP/2021-06-18_*.md")
```

用途：`key_facts` / `summary` 覆盖不到的**深层事实**——团队成员、技术路线、
客户名单、产品参数、业务模式。这些字段 structurer 不抽取，只在正文。

### P3 · 证据核验（进答案前的强制一道）

范围：`## 原文证据` 三列表（字段 / 值 / 原文片段）。

对每个要进答案的数值：在 `## 原文证据` 找到同一 `字段`，核对 `值` 与 `原文片段` 是否自洽。

| P3 结果 | 处理 |
| --- | --- |
| 值在片段中逐字出现且语义一致 | 可用，正常引用 |
| 值在片段中但语义错位（单位、主语、口径） | 标「未核实」，引用时注明问题 |
| `## 原文证据` 无该字段 | 回正文逐字找；找不到 → 「未核实」 |
| 片段本身是乱码/不可读 | 标「未核实」+ 提取异常 |

**核实失败不等于结论错误**，只是**不能当作已核实结论**。删掉它才是错的——
用户需要知道「库里是这么写的，但它有问题」。

### 实测已知的 P3 高风险模式

| 模式 | 实测样本 | 表现 |
| --- | --- | --- |
| 单位被截断 | 米格实验室 `投后估值: 2亿人` | 原文是「2亿人民币」，正则切到了「人」 |
| 主语错位（行业标杆） | 云潼科技 `成立时间: 2005年` | 原文说的是斯达半导体成立 2005 年 |
| 行业通用值冒充主体值 | 长城证券 REPORT `营收: 42.50亿` | 原文是 SK海力士 22Q4 营收 42.50 **亿美元** |
| 投前值填进投后字段 | 利之达科技 `投前估值` 与 `投后估值` 同为 2亿元 | 原文只有「投前估值2亿元」 |

这四类都能通过 P1 命中，**只有 P3 能拦下**。遇到时按「标未核实 + 说明」处理，
不得替上下游修正，也不得把修正后的值当结论。

## 三、主体别名解析

主体在库里有 7 个可检索位置，**按命中可靠性降序**：

| 序 | 位置 | 说明 | 实测填充率 |
| --- | --- | --- | --- |
| 1 | `subject` | 规范简称，最稳定 | 172/172 |
| 2 | 文件名 | 与 `subject` 一致 | 172/172 |
| 3 | `alias_short` | 通常等于 `subject` | 172/172 |
| 4 | `alias_full` | 工商全称 | 37/172 |
| 5 | `tags` | 赛道词 + 主体 + 别名 | 部分 |
| 6 | 正文 `entity_key` | dedupe 块内的归一化键 | 172/172 |
| 7 | `alias_en` | 英文名（仅主体本身是拉丁字母时） | 6/172 |
| 8 | `alias_pinyin` | 拼音首字母 | **0/172** |

### 解析顺序与降级

```
用户口语
  ↓ ① 直接 grep（用户原词）
  ↓ ② 去地域前缀后 grep（深圳市/重庆市/苏州市/浙江省…）
  ↓ ③ 补常见后缀后 grep（有限公司 / 股份有限公司 / 科技 / 半导体）
  ↓ ④ 英文/缩写 ↔ 中文并查（SiC ↔ 碳化硅；IGBT ↔ 绝缘栅双极晶体管）
  ↓ ⑤ entity_key 归一化匹配（去空格/标点/大小写）
  ↓ ⑥ alias_pinyin —— 全库为 null，直接跳过，不报错、不臆造
  ↓ 仍无命中 → 「主体未收录」，列出尝试过的写法
```

**降级原则**：某一步字段为 `null` 就跳过这一步，不当作错误。
`alias_pinyin` 全库 0 条非空是**数据现实**，不是缺陷；
用户用拼音搜时，应回答「本库未生成拼音索引，请提供中文名」，而不是猜。

### 实测的多主体同 entity_key（必须辨析）

dedupe 会把同一实体归一，但 `subject` 可能不同。命中多个 `subject` 时，
**先判断是不是同一家**，再决定是否合并展示：

| entity_key | 涉及 subject | 判断 |
| --- | --- | --- |
| `森国科sic` | 森国科SiC / 森国科碳化硅SiC | 同一家，其中一份是 `duplicate_of` |
| `云潼科技` | 重庆云潼科技 / 云潼科技 | 同一家，两份 BP，**轮次与所在地区冲突** |
| `中熵科技` | 中熵科技 / 中熵科技项目 | 同一家，**跨赛道**（半导体 / 新材料），轮次冲突 |
| `华拓半导体技术` | 深圳市华拓半导体技术 ×2 | 同一家，两份 BP |
| `赛迪译丛` | 赛迪译丛 ×3 | **同一发布机构的 3 份不同报告**，不是同一主体 |

最后一行是关键：`entity_key` 相同**不代表**是同一公司。REPORT 的 `subject` 是发布机构，
同一机构的多份报告会共享 `entity_key`，合并它们会把不同报告的内容串味。

## 四、时间排序

### 权重

```
doc_text   = doc_meta   >   filename   >   fs_mtime   >   unknown
   （原件落款 / 文档属性）      （文件名）    （文件系统时间）
```

### 规则

1. 先按权重分层，同层内按 `date` 降序。
2. **`fs_mtime` 不得用于「最新优先」**：它只反映拷贝时间。
   实测 2 份：沙利文的报告显示 `2026-07-28`，但标题写的是「2023 中国半导体石英坩埚」；
   `2026-10-30` 的 NOTE 也是拷贝时间。把这类日期当时间线会得到错误结论。
3. `unknown` 排最后，且不参与「最新」判定。
4. 日期精度不一（`2022-05` / `2022` / `2022-05-15`）时，**按字符串前缀比较**即可，
   但展示时不得补全缺失的日/月。

### 实测分布

| date_source | 份数 |
| --- | --- |
| doc_meta | 89 |
| doc_text | 51 |
| filename | 30 |
| fs_mtime | 2 |
| unknown | 0 |

## 五、回溯

**触发**：当前命中文档不含目标概念，但主体确实存在。

```
当前（最新）文档无该概念
  → 展开同 entity_key 的全部文档，按权重排序
  → 逐份 P1 → P2 检索
  → 全部遍历仍无 → 「该主体已收录，但未包含 <概念>」
```

**与「未收录」区分**：

- 「主体未收录」：grep 无任何命中
- 「该主体已收录，但未包含 X」：主体命中，X 遍历无果 ← **这是更有信息量的答案**
- 「可能因降级而漏检」：命中文件里含 `needs_ocr` / `encoding_error` / `corrupt` 状态，
  不得声称「一定没有」

## 六、覆盖报告

每次检索都必须能回答这四问，写进输出末节：

```
- 检索路径：{实际执行的 glob，逐条列出}
- 关键词：{实际执行的 grep 词，含中英并查项}
- 命中 / 实读：命中 N 份，实读 M 份（M ≤ 8）
- 未纳入：{文件 + 原因：超预算 / 状态降级 / 无相关段落 / duplicate_of}
```

**「未纳入」不是免责声明，是结论的一部分**：读不完就必须说清楚没读什么，
否则用户会以为「没读到 = 不存在」。
